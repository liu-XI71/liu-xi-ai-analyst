# 架构与执行边界

产品围绕一个完整业务任务组织：明确指标和 cohort，确认数据可用，执行分析，给出有证据的决定，再保存复查记录。

## 分层

| 层 | 实现 | 职责 |
|---|---|---|
| 展示 | 原生 HTML/CSS/JavaScript | 业务概览、动态分析、案例、实验、监控、证据与报告 |
| API | FastAPI/Pydantic | 结构化请求、字段校验、运行记录、导出、反馈 |
| 编排 | OpenAI Responses 有界工具循环 | 上下文、指标选择、计划、质量、SQL、业务分析、报告重点 |
| 业务计算 | Python/参数化 SQL | 新用户留存与漏斗、变化分解、实验统计、复购预算 |
| 语义 | 版本化 JSON 与业务 Skill | 指标定义、维度、窗口、成熟、失败分支 |
| 数据 | SQLite | 匿名用户/事件/分配/结果、批次水位、业务变更、运行与告警 |
| 验证 | pytest 与公开回归集 | 原始数据复算、数据损坏、统计边界、证据重放与接口 |

运行时使用一个编排器与专门工具。关键数字由业务函数产生，模型从已有事实中选择报告重点。SQL 工具是补充核验入口，采用语法树、只读连接、SQLite authorizer、表范围、时限与行数约束。

## 四个业务域

- onboarding：主要增长项目，110 日注册范围，精确 D1/D7、窗口回访、24h有序激活，数据延迟与恢复快照。
- experiments：预注册随机实验；健康、SRM、围栏、未成熟、样本不足、非等流量、改参与采集缺口。
- repurchase：正向订单、成熟复购、截止日 RFM、预算候选与留出计划。
- growth：保留的早期次7日内回访域，用于兼容与回归；不等同精确 D7。

增长诊断与实验评审使用不同的合成数据集。实验结果说明评审方法，不声称是已经对增长异常实施修复得到的实际收益。

## 证据链

每条事实指向证据 ID，证据包含实际 SQL、参数、结果行、指标版本和数据来源。分析结果保存请求、运行时间、应用版本、口径与执行记录。静态导出增加数据指纹和回放标记。

数据质量失败时，相关业务指标保持缺失或不输出；不会因报告需要完整布局而填入 0。不同指标独立判定观察成熟。24h 转化与自然日 D1/D7 分别计算。

告警保存唯一键、首次/末次观测、状态和迁移历史。数据回填可以关闭数据告警；业务指标仍下降时，业务告警继续存在。重复执行同一快照复用已有批次，不重复制造报警。

## 模型与产品记录

模型流程使用严格工具参数与有限重试，显式条件不得被模型静默修改。无 Key、无配额、调用错误或超过轮次均返回失败，不伪装已完成。

技术遥测不保存原始问题、IP 或身份；记录模式、状态、耗时、工具与 token。独立运行表保留分析请求以支持结果复现。公开实例仅提供合成数据分析，输入框不应提交企业或个人敏感信息。私有数据接入需独立认证、数据权限与保留策略，当前只读约束不是企业级行列权限系统。

反馈采用每次运行独立凭证，只存凭证哈希；同一运行更新评价不会重复计数。完成请求、用户自评与经基准核验的任务成功是三种不同指标。

## 部署

GitHub Pages 承载静态作品与预计算案例；Python 服务承载新的查询和模型调用。两者通过可配置 API 地址连接。单实例演示使用 SQLite；持久化与调度由部署环境负责。云端在线、模型响应、数据实时刷新分别验收。
