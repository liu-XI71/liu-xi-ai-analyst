# 复购场景：数据、口径与复现

当前复购业务域用于演示可验证的数据分析流程。1200名客户、订单和地区均由固定种子生成，绝不代表刘希、原作品集、实习公司或任何真实企业的客户与经营业绩。没有真实联系方式、营销同意、触达记录、退款、成本或随机实验结果。

## 来源与个人实现

业务口径参考刘希已有的[复购运营项目](https://github.com/liu-XI71/liu-xi-evidence-analytics)中`analytics.py`的成熟队列与正向交易额定义，以及`operations.py`的时点分群边界。旧作品使用UCI Online Retail；本项目**没有复制UCI交易明细**，完全重新生成演示数据，不把模拟订单标成公开数据集实测结果。

新增实现是命名隔离的SQLite明细、真实SQL与参数证据、请求校验、窗口与地区筛选、预算计划、稳定种子留出分配，以及与共享API输出合同兼容的图表、事实和报告结构。

## 生成规则与数据库

- 数据范围：2026-01-01至2026-06-30，观察截至日固定为2026-06-30。
- 生成种子：`7102026`，由Python标准库`random.Random`驱动。
- 客户数：1200。客户ID是`SYN-`前缀的固定哈希；订单ID也使用`SYN-`前缀。
- 地区：华东、华南、华北、西部，合成权重分别4、3、2、1。
- 每位客户被随机赋予首个购买日和后续购买倾向，并加入少量首日多订单。华南5月起的购买概率设置了演示用变化；这是生成器假设，不是数据推导出的真实营销机制。
- 金额以整数分保存，只接受正数。界面展示CNY是模拟货币单位，不是实际财务账。

`repurchase_customers(customer_id, region)`存匿名客户；`repurchase_orders(order_id, customer_id, order_date, amount_cents)`存正向订单；`repurchase_metadata(key,value)`保存版本、日期、来源和种子。表名带业务前缀，避免污染增长域。

`build_database(path)`幂等创建当前版本；不会修改其他业务域表。`analyze(request,path)`使用SQLite只读URI连接，不写入名单、不触达客户。

## 时间与指标合同

| 内容 | 实际含义 |
|---|---|
| 队列选择 | 先在全量数据识别每位客户的首次观察购买日，再筛选`start`至`end`（两端包含） |
| 次7日内复购 | D1—D7至少一笔正向订单；分母须完整观察至D7 |
| 次30日内复购 | D1—D30至少一笔正向订单；分母须完整观察至D30 |
| 成熟判断 | 使用固定快照2026-06-30；未成熟客户即使提前复购，也不进入该成熟分母 |
| 30日人均正向交易额 | 完整观察D30客户的D0—D29正向订单金额/成熟客户数；包含首单，不是净LTV |
| RFM的R | 截止日`end`距最后一笔已观察订单的天数 |
| RFM的F | `end`及之前全部观察历史订单数，包含同日多单 |
| RFM的M | `start`至`end`窗口正向交易额；改变start会真实改变M和候选排序 |
| 历史金额 | `end`及之前全部观察正向交易额，用于候选排序的次级依据 |
| 对照 | diagnose/report可提供compare_start/compare_end；两组统一观察至同一快照日 |

候选和结果使用不同的时间边界。截止日之后的订单可以用于成熟队列结果，但**不能**用于截止日候选生成与排序。代码与测试分别验证这两个约束。

单笔历史订单按R≤30和R>30分为“近期单次购买”“单次购买沉默”。多笔历史订单按R≤30、31—60、>60分为“活跃复购”“31—60日未购”“60日以上未购”。这是可解释的运营规则分群，不是模型预测、最优RFM阈值或购买频次分位评分；多订单同日购买不自动构成D1之后复购。

## 预算与留出计划

默认预算200元，每位处理组客户计划成本2元，留出比例20%，候选上限100人，seed为`liuxi-2026`。这些是可修改的计划假设，不是观测到的真实成本。

默认候选只选择多订单且最近31日以上未购的客户；指定单一segment时可以查看其他分群。候选按窗口金额降序、历史金额降序、最近购买间隔升序、匿名ID排序，名单不包含未来结果。

处理容量为`floor(预算分/每人成本分)`。系统同时满足人数上限、可用候选数和预算，按`floor(n×留出比例+0.5)`确定实际留出人数。对候选按`SHA-256(seed:customer_id)`排序，前若干名分配为留出，其余计划处理。整数舍入可能使实际比例不同于请求比例；实际人数和比例会随结果返回。小样本可能没有留出，只能演示流程；代码会给出样本量说明。

同一数据、日期、筛选、预算和seed完全复现；改变seed仅改变处理/留出分配。分配后用整数分核算预算，不产生货币浮点溢出。0预算返回空候选和数据/预算不足状态。

预算被视为“每位计划处理客户最大成本”的上限；实际接入优惠券时，需重新定义成本与核销关系，不能把这个计划数字当实际支出。这里没有触达执行，也没有对自然交易进行实验增量估计。

## 请求示例

```json
{
  "question": "截至5月底，在200元预算内生成复购召回候选与留出计划",
  "domain": "repurchase",
  "task": "report",
  "start": "2026-03-01",
  "end": "2026-05-31",
  "filters": {
    "region": "all",
    "segment": "all",
    "budget": 200,
    "contact_cost": 2,
    "holdout_ratio": 0.2,
    "seed": "liuxi-2026",
    "limit": 100
  }
}
```

`diagnose`只使用region筛选；`segment`不支持对照窗口，要求改用`diagnose`/`report`；`report`中的segment只影响分群和候选，队列仍按首次日期与地区定义。未知筛选、非法日期、负预算、0成本等返回`needs_clarification`，不静默采用默认值。缺少成熟分母返回空指标，不编造0%或将未成熟用户当流失。

## 证据与验收

每次SQL证据包含完整SQL、实际绑定参数、原始行、数据来源和指标版本。候选SQL可能返回少量随后被预算截去的末位记录；其原始行保持原样，最终名单与明确的确定性分配算法共同解释实际结果。SQL可在相同快照上重放。

测试命令：

```bash
python -m unittest discover -s tests -p test_repurchase.py -v
```

当前12项测试覆盖固定种子复现与幂等、D0排除/D7/D30边界、成熟分母、D0—D29金额、未来订单不影响历史候选、日期真实生效、预算/seed、0预算、地区与空数据、非法参数、对照日期，以及全部SQL证据逐条精确重放。它们验证确定性业务域，不代表真实模型已经通过语言理解评测，也不证明营销策略有效。
