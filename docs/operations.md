# 运行监控与产品反馈

## 日级监控

运行 `python scripts/run_monitor.py --scenario business_drop` 会实际执行新用户分析并保存监控批次。`late_data` 和 `recovered` 使用同一份事件的不同到达快照，能够复现到数阻断、回填与重新计算。

- 幂等键来自场景、指标合同、质量状态和实际 KPI。
- 相同快照重复运行返回相同运行编号，并标记 reused。
- 数据质量告警独立于留存业务告警；缺数时业务告警等待数据，恢复后重新判断。只有分析状态为 `completed` 且质量状态明确为 `passed` 才能解除质量告警；未成熟、空 cohort 或无法评审的结果保持 `data_waiting`，不写成数据已恢复。
- 演示业务规则使用下降不小于2个百分点的固定阈值，展示生命周期；该阈值不是生产历史校准结果，也不代表统计显著。
- 定时运行可由外部日级调度器调用同一命令。仓库提供实际可执行批次，不将静态回放称为持续在线监控。

`GET /api/v1/monitoring` 返回 jobs、alerts、transitions 与规则。管理员可使用 `POST /api/v1/monitoring/run` 触发；公开无令牌请求不能改变监控状态。

## Agent 使用分析

技术运行记录包括模式、域、状态、耗时、工具次数、工具失败及真实模型返回的 token。原始问题、IP、姓名和邮箱不进入这张遥测表。

已经进入模型执行但因 Provider、工具校验或轮次上限失败的任务，也记录为 `failed`。记录仅包含脱敏阶段、错误类型、耗时与已观测用量，不保存原始问题、工具参数或 Provider 错误正文。缺少配置的请求单独标为配置失败。

Token 完整性使用 `complete`、`partial`、`unknown`、`not_applicable`：真实模型未返回的用量保持未知。存在未知或部分用量时，汇总 `input_tokens/output_tokens` 为 `null`，`known_input_tokens/known_output_tokens` 仅表示已经观测到的部分。它们不能解释为完整消耗或零费用；没有价格合同就不生成费用估计。

`completed` 仅代表流程完成；是否正确要对照基准或人工 rubric。调用次数不能推导独立用户数，模型调用也不自动产生用户采纳和业务收益。

结果页支持自愿提交有用、需要修改、结果不正确或未完成，以及问题理解、指标、时间窗口、工具、证据和交付等失败分类。每次运行只保留最新评价，人工核对分钟数为可选项。

## 实时任务配额

先鉴权，再取得并发执行槽位，最后预留 UTC 日额度。鉴权失败、并发繁忙和已超日额度的拒绝不增加用量。每个被接纳进入模型执行的分析任务占用一次日额度，即使随后 Provider 或工具执行失败也计入；同一任务可能包含多轮 Provider 调用，日额度不是单轮 API 调用计数或美元账单上限。日计数位于持久 SQLite，进程内限流重置不会恢复日额度。

实时工具参数与业务 API 保持同一类型：渠道、设备和版本支持单值或列表；复购分组种子接受整数或文本，明确传入的筛选不能被模型静默改写。

## 小规模试用记录规范

真实试用开始后，以匿名参与者和预先定义任务记录：预期答案、完成过程、澄清、失败、人工修订、结果判定与耗时。当前公开版本不预填参与人数或满意度。

比较手工 SQL/Python、确定性工具和 AI 三种方式时，平衡任务与顺序，分开记录系统等待与人工检查时间。选一个实际失败进行改进，并使用不同任务复测。小样本研究不用于推断整体市场留存或总体满意度。
