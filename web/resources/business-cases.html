01｜新用户下滑：先分清人群变化与路径问题

业务场景与待做决定

新注册用户数量增加，精确 D7 留存下降。分析目标：量化变化，拆分人群结构与组内表现，定位转化下降的路径环节，制定干预验证方案。

分析顺序：指标口径 → 数据质量 → 联合分层 → 路径与版本 → 验证事项 → 行动方案。核心数值使用固定口径的 SQL 与 Python 计算。

数据范围与口径

  • 当前注册 cohort：2026-08-24—08-30；对比 cohort：2026-08-17—08-23。两期均为 7 个自然日，按稳定匿名 UID 去重。
  • 精确 D7：注册后第 7 个自然日有 app_active 的 cohort 用户数 / 完成完整观察且到数完整的 cohort 用户数。时区 Asia/Shanghai。
  • 24 小时路径：注册 → 引导完成 → 首屏成功 → 单次有效内容消费 ≥60 秒。后一步严格晚于前一步，全部发生在 [注册时间, 注册时间 +24h) 内。
  • 快照截止 2026-09-19 08:00，连续水位 2026-09-19 00:00；所需 D7 窗口结束于 2026-09-07 00:00。质量门禁通过。

证据：onboarding-cohort-scope、onboarding-batch-watermark、onboarding-event-validation。

02｜延迟与恢复：数据回填与同口径重算

业务场景与待做决定

同一批注册用户已经走完 D7，但某些事件尚未进入分析库。产品或运营负责人需要决定：当前看板是否足以支持预算调整和产品决策，还是应先联系数据链路负责人处理缺口。关键在于区分“观察时间到了”与“数据完整到了”。

数据与快照

该案例与案例 01 使用同一份注册与事件数据、同样的两期 cohort 和精确 D7 口径。只改变读取截止时间，所有事件按 ingested_at 过滤。指标按实际可见事件计算，质量不通过时保持缺失。

指标可用性逐项判断：本次 D1 只需要覆盖到 9 月 1 日零点，已满足条件；精确 D7 与次 1—7 日回访需覆盖到 9 月 7 日，尚不满足。纯 iOS cohort 可使用自身已完整分区，不能把 Android 的延迟泛化成所有用户都不可分析。

回填结果与业务差异

回填快照水位推进到 9 月 8 日零点，原 cohort 重算得到 D7 191 / 898 = 21.269%，与完整快照一致；对比期为 233 / 856 = 27.220%。质量恢复后，前后期业务差异仍然存在。回填后数据可用，D7 的前后期差异仍为负。

待区分的问题证据处理
是否仅仅等待用户完成观察？读取时间已晚于该 cohort 的完整 D7 日终观察成熟通过，继续检查到达而非延长 cohort
是否已知批次缺失？三个 Android 批次应到计数大于当前可见计数定位分区并回填，保留原 cohort 与原指标版本
回填是否消除了前后期差异？回填结果与完整快照一致，但 D7 差异仍为 -5.950 pp回到案例 01 的结构与路径分析，避免过早结案

行动与复查条件

  • 将受影响的设备、事件日、应到和已到计数交给数据链路负责人核对；保留原始分析参数与快照标识。
  • 回填必须通过源端计数、连续水位、事件版本与关联校验；未通过前保持质量告警状态。
  • 在同一 cohort、同一口径、同一筛选下重算，再比较恢复快照和完整快照的结果，避免使用不同人群掩盖差异。
  • 已知源端清单只能覆盖已登记批次；源端未记录的漏报仍需埋点与采集侧专项核查。

关键 SQL 与交付物

完整查询：onboarding-batch-watermark；参数随快照保存
SELECT b.event_date,b.device,b.expected_events,COUNT(e.event_id) AS observed_events,
      MAX(e.ingested_at) AS latest_arrival
      FROM onboarding_ingest_batches b LEFT JOIN onboarding_events e
        ON e.batch_id=b.batch_id AND e.ingested_at<=:as_of
      WHERE b.event_date BETWEEN :batch_start AND :batch_end
        AND b.manifest_available_at<=:as_of AND b.device IN (:quality_device_0,:quality_device_1,:quality_device_2)

该查询先将事件按可见到达时间与源端批次对齐，再逐设备检查连续日期。交付包括受影响指标、分区缺口、停止原因、复查条件与恢复证据；SQL 参数在对应快照中完整保存。

03｜主指标正向，体验围栏恶化：停止或调整

独立实验数据： 本案例使用种子 7109 生成的独立随机分配与结果日志，与案例 01 的诊断 cohort 不属于同一次实验。它用于验证实验评审方法，不代表已经实施了前述修复，也不能作为前述修复的收益证明。

业务场景与待做决定

产品负责人拿到一份 D7 正向的实验结果，需要决定是否扩大覆盖。运营层面还关心：提升是否来自可接受的体验代价，数据链路和随机分配是否可靠，以及样本与观察窗口是否满足预注册要求。

预注册合同与健康度

  • 固定入组窗口：2026-08-17—08-30；观察数据截至 2026-09-07 00:00（排他上界）。随机单位是新注册用户，预期 1:1 分配。
  • 使用 ITT，按原始分配组比较；未曝光用户仍在分母，不按事后活跃或成功曝光筛选。
  • 主指标：精确 D7；基线 28%，样本规划 MDE 为 2.5 pp，双侧 alpha=0.05、功效 80%。放量业务门槛另设为效应 95% 区间下界至少 1 pp。MDE 与放量门槛解决不同问题。
  • 24h 负反馈围栏：基线 4%，可接受恶化界值 1.5 pp；用单侧 97.5% 上界进行非劣判断。
  • 分配、身份、配置、采集、事件与成熟检查均通过。SRM p=0.009959，高于此协议固定使用的 0.001；阈值不在看到结果后更改。

设计所需样本为每组 5,196 人，共 10,392 人。实际对照 8,163 人、处理 7,837 人，两组均达到要求。SRM 通过只意味着该项门禁未触发，不是对所有潜在数据问题的保证。

证据：experiment-registry、experiment-quality、experiment-changes、experiment-groups。

结论适用范围

问题已有证据仍需检查
是不是随机分配或到数失真？原始分配人数、身份、配置和采集门禁通过SRM 与对账不能替代业务埋点语义核查
是否以更强干扰换取短期回访？D7 正向且 24h 负反馈明显恶化需进一步看机制、反馈类别和受影响人群；不能凭聚合表断言具体心理机制
能否只保留表现好的子群后宣布成功？当前主要结论基于预注册总体 ITT事后子群属于探索；独立复测前不替代总体结论
能否外推长期价值？当前只覆盖 D7 和 24h 围栏长期 LTV、组合效应和长期 Holdout 是不同问题

行动与验证方案

保持不放量，先检查体验机制及负反馈类型；若调整处理方案，登记新的实验版本与观察窗口，不在原实验中混合新旧方案。冻结主要指标、围栏、样本和分析规则后重新执行。每日出现显著结果不自动提前结束固定窗口实验。系统交付评审意见，不执行产品开关或营销动作。

关键 SQL 与交付物

完整查询：experiment-groups；ITT 包含未曝光分配用户
WITH users AS (
 SELECT a.user_id,a.arm,date(a.registered_at) AS cohort_date,
  CASE WHEN datetime(date(a.registered_at),'+8 days')<=:cutoff
    AND datetime(a.registered_at,'+24 hours')<=:cutoff THEN 1 ELSE 0 END AS mature,
  EXISTS(SELECT 1 FROM experiment_exposures e WHERE e.experiment_id=a.experiment_id AND e.user_id=a.user_id) AS exposed,
  EXISTS(SELECT 1 FROM experiment_outcomes o WHERE o.experiment_id=a.experiment_id AND o.user_id=a.user_id
    AND o.event_name='qualified_activity'
    AND o.event_at>=datetime(date(a.registered_at),'+7 days')
    AND o.event_at<datetime(date(a.registered_at),'+8 days') AND o.ingested_at<:cutoff) AS retained_d7,
  EXISTS(SELECT 1 FROM experiment_outcomes o WHERE o.experiment_id=a.experiment_id AND o.user_id=a.user_id
    AND o.event_name='negative_feedback' AND o.event_at>=a.registered_at
    AND o.event_at<datetime(a.registered_at,'+24 hours') AND o.ingested_at<:cutoff) AS negative_feedback
 FROM experiment_assignments a WHERE a.experiment_id=:experiment_id
)
SELECT arm,COUNT(*) AS users,SUM(mature) AS mature_users,SUM(exposed) AS exposed_users,
 SUM(CASE WHEN mature=1 THEN retained_d7 ELSE NULL END) AS retained_users,
 SUM(CASE WHEN mature=1 THEN negative_feedback ELSE NULL END) AS negative_users
FROM users GROUP BY arm ORDER BY arm

交付包括预注册参数、分配与采集检查、样本规划、效果与围栏区间、逐项门禁及明确的停止理由。两组人数不相同，效果使用组内比例之差，不能直接把回访人数 2,612 − 2,284 当作干预增量。

04｜复购预算：把规则分群变成可验证的行动计划

业务场景与待做决定

用户运营负责人有 200 元演示预算，希望从近期不再购买的客户中确定一组规则明确的候选，同时保留评估增量的比较组。任务包含三个约束：分群只能使用决策时点已知的信息，费用不能超预算，计划必须与已经发生的营销结果明确区分。

数据与时点

  • 候选截止日为 2026-05-31；窗口交易额 M 只累计 2026-03-01—05-31 的正向订单。
  • F 使用 2026-01-01—05-31 已观察订单数；R 是截止日距最近正向购买的天数。候选排序不读取 6 月订单。
  • 历史 cohort 的复购结果统一观察至 2026-06-30。结果评估可以使用观察窗内的后续订单，但不能让这些未来订单回流进 5 月 31 日的候选排序。
  • 全量明细中的首次观察购买不等于真实首次获客。正向交易额未扣退款、成本，也不等于净 LTV、利润或 ROI。

证据：rp-cohort、rp-segments、rp-candidates；合同版本 repurchase-1.0.0。

历史基础：两种分母分别报告

3 月至 5 月的首次观察购买 cohort 为 616 人，其中次 7 日内复购 62 / 616 = 10.065%，次 30 日复购 175 / 616 = 28.409%。首个观察购买日起 D0—D29 的人均正向交易额为 225.10 元。这些是历史描述，不能视为本次候选触达后的结果。

截至 5 月 31 日的 RFM 分群包含 1,005 人。它与 616 人的首次观察购买 cohort 不是同一个分母：RFM 包含更早已购买且截至日已知的客户。

预算方案：100 名候选、80 名计划处理、20 名留出

默认候选来自“31—60 日未购”与“60 日以上未购”，按所选窗口交易额、历史交易额、最近购买及稳定 ID 排序。当前候选包含 77 名 31—60 日未购客户、23 名 60 日以上未购客户。排序只反映规则优先级，未估计干预响应或营销增量。

预算/分配项实算值含义
预算上限200 元演示配置，不代表实际付款
每位处理客户计划成本2 元不对留出客户计触达成本
候选上限floor(200 / 2) = 100 人先按预算得到保守候选上限
计划处理 / 随机留出80 人 / 20 人在候选内，以固定种子稳定散列形成可复现分配
计划处理成本80 × 2 = 160 元低于预算；剩余 40 元未分配

当前算法先限制候选数，再在其中划出留出组，因此没有把 200 元预算用满。若业务目标改为用满预算，需要先重定义候选上限和留出比例规则，再冻结新计划；不能把留出客户事后加入触达来“补预算”。对比组的完整保留是后续估计增量的必要条件之一。

关键 SQL 与交付物

完整查询：rp-candidates；候选排序仅使用截止日前订单
WITH history AS (
 SELECT o.customer_id,c.region,MIN(o.order_date) AS first_date,MAX(o.order_date) AS last_date,
 COUNT(*) AS frequency, SUM(o.amount_cents) AS history_value_cents,
 SUM(CASE WHEN o.order_date>=:start THEN o.amount_cents ELSE 0 END) AS window_value_cents,
 CAST(julianday(:end)-julianday(MAX(o.order_date)) AS INTEGER) AS recency
 FROM repurchase_orders o JOIN repurchase_customers c USING(customer_id)
 WHERE o.order_date<=:end AND (:region='all' OR c.region=:region)
 GROUP BY o.customer_id,c.region
), rfm AS (
 SELECT *,CASE WHEN frequency=1 AND recency<=30 THEN 'first'
  WHEN frequency=1 THEN 'single' WHEN recency<=30 THEN 'active'
  WHEN recency<=60 THEN 'cooling' ELSE 'dormant' END AS segment
 FROM history
)
SELECT customer_id,region,recency,frequency,window_value_cents,history_value_cents,segment
 FROM rfm WHERE ((:segment='all' AND segment IN ('cooling','dormant')) OR segment=:segment)
 ORDER BY window_value_cents DESC,history_value_cents DESC,recency ASC,customer_id LIMIT :limit
